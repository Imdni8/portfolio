<Chapter id="problem">
<StoryChapter heading="Problem" narrow>
<Fragment slot="intro">

> User had to choose the right agent and keep all MCPs authenticated before they could start a conversation, leading to high setup friction

The reason for having multiple agents was that each one could be audited and approved for
specific tasks, which is great for compliance. But it also forced user to find the right agent
before delegating their task. Bolt was conceived for solving this problem.

</Fragment>

<Figure
    src={problemAgentList}
    alt="The agent list in Agent studio — five agent cards, each with its own description and version, and a Create Agent button"
/>

</StoryChapter>
</Chapter>

<Chapter id="identity">
<StoryChapter heading="Bolt's identity" narrow>
<Fragment slot="intro">

To differentiate Bolt from the rest of the agents, and give it more emphasis, I felt Bolt
needed its own identity.

I began by asking what feeling it should evoke — fast, instantaneous, energetic, raw. I studied
images of bolts and thunder to finalise the following visual metaphors: sharp curves, dynamic,
asymmetry.

I explored 6–7 variations to arrive at the final logo.

</Fragment>

</StoryChapter>

<Chapter id="embedding">
<StoryChapter heading="Embedding Bolt in Agent studio" narrow>
<Fragment slot="intro">

> Conversations with Bolt should feel like group chats between the user, Bolt and other agents Bolt “invites” to the chat

When I began designing the Bolt experience, I asked myself how would the user relate to Bolt.
After discussing with the PM, I proposed conversations with Bolt to be like group chats between
the user, Bolt and other agents Bolt “invites” to the chat. Additionally, I was also solving for
how user will find and interact with Bolt, for example, start a new chat and view previous chats.

Some directions explored and dropped…

</Fragment>

<StoryBlock>

<Figure
    slot="visual"
    src={directionGlobalChat}
    alt="The agent list with a global Bolt chat summoned over the whole product surface"
    caption="Direction 1: Global chat"
/>

I liked the idea of “summoning” Bolt anywhere on the product surface. But the complexity of
managing previous chats and keeping current chats in context while allowing user to move around
the product snowballed. Also, it required a big UI nav revamp which I wasn't sure of committing
to without validating the efficacy of this approach. Leading me to drop this idea for the time
being.

</StoryBlock>

<StoryBlock>

<Figure
    slot="visual"
    src={directionSideChat}
    alt="The agent list with Bolt docked as a side chat panel on the right, narrowing the content area"
    caption="Direction 2: Side chat"
/>

Side chat has come up in a lot of enterprise products lately. I tried it but decided against it
because it obstructed the view and added a lot of visual clutter to an already information dense
screen.

</StoryBlock>

</StoryChapter>
</Chapter>

<Chapter id="solution">
<StoryChapter heading="Solution" narrow>
<Fragment slot="intro">

I designed Bolt as the single point of intake for every task — handing it off to the right
specialised agents automatically, letting users tag agents directly when they already know who
should do the work, and keeping the conversation moving even when a connector's credentials have
expired.

</Fragment>

<Chapter id="reflection">
<Reflection narrow>

Next time, I'd invest earlier in the motion that shows the system's state — the handoff banner, the tool-call list filling in as each agent works, the auth sheet opening inline. Those moments carry more information about what's actually happening than any static label could, especially in a product where several agents can be working at once and the user has no other way to tell who's doing what.

I treated motion as a polish pass at the end of the sprint. It deserves to be a design decision from the start, made alongside the interaction logic itself, not layered on after.

</Reflection>
</Chapter>
