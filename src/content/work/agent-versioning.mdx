<Chapter id="context">
<StoryChapter heading="Context" narrow>
<Fragment slot="intro">

Agent studio helps customers create, deploy and monitor agents for running their clinical
trials. It comes with pre-built agents, or users can create custom agents as well.

For example, a <Term id="cra">Clinical Research Associate</Term> (CRA) can build an agent to monitor non-compliant events in the clinical trials they're overseeing.

</Fragment>

<Figure
    src={contextAgents}
    alt="Four agent cards from Agent studio: Clinical Monitoring, eTMF Management, PI Summary and Review, and Build your own agent"
    caption="Pre-built agents, and the option to build your own"
/>

</StoryChapter>
</Chapter>

<Chapter id="problem">
<StoryChapter heading="No versioning, no governance" narrow>
<Fragment slot="intro">

> Lack of versioning stalled adoption by customers, hurting revenue

Any change made to an agent overwrote its previous configuration and went live immediately.

This meant customers couldn't validate agents before letting them access their clinical trial
data. Overwriting was also a problem because it prevented auditing: once a configuration was
gone, there was no record of what the agent used to do.

</Fragment>

<Figure
    src={problemCanvas}
    alt="The agent canvas before versioning: a single draft agent with Settings, Test, Save and Publish, and no version history"
    caption="The agent canvas before versioning"
/>

</StoryChapter>
</Chapter>

<Chapter id="versioning">
<StoryChapter heading="How does versioning work?" narrow>
<Fragment slot="intro">

An agent is made of various <Term id="dependency">dependencies</Term> like a system prompt, skills, etc. When one of them is modified, every agent using it receives an update. **Changing any dependency or updating it increments the agent's version.**

</Fragment>

<Figure
    src={versioningModel}
    alt="A diagram: Agent v1, made of a system prompt, skills, knowledge, guardrails, connectors and triggers, receives an update (one or many, optional or mandatory) and becomes Agent v2"
/>

</StoryChapter>
</Chapter>

<Chapter id="goals">
<StoryChapter heading="Design goals" narrow>
<Fragment slot="intro">

The best agent versioning experience will…

<div class="mx-auto grid w-full max-w-[var(--measure-copy)] gap-4 grid-cols-[repeat(auto-fit,minmax(14rem,1fr))]">
  <GoalChip>Help users intuitively keep track of an agent's versions and state: draft or published</GoalChip>
  <GoalChip>Handle multiple updates gracefully and help decide which ones are worth accepting</GoalChip>
  <GoalChip>Prevent users from publishing while mandatory updates are missing</GoalChip>
  <GoalChip>Allow reverting to a previous version when necessary</GoalChip>
</div>

</Fragment>
</StoryChapter>
</Chapter>

<div class="grid gap-[var(--spacing-xl)]">

<p class={[storyProse, 'w-full max-w-[var(--measure-copy)] mx-auto'].join(' ')}>The dependency card was already used to edit a dependency's configuration. I redesigned it to handle updates on top of it.</p>

  <Figure

<div class="grid gap-[var(--spacing-xl)]">
<h3 class="story-subhead">How to handle state change?</h3>
<p class={[storyProse, 'w-full max-w-[var(--measure-copy)] mx-auto'].join(' ')}> State changes was the most important because what the user could or couldn't do depended on the state. My biggest insight driving this design was that version number is not important and that change of state should be made explicitly clear. </p>

  <Figure
    src={stateChange}
    alt="Three concepts: 'Version 6' beside a Draft tag; an Unpublished tag with a Draft menu listing v5 as published; and a yellow banner reading 'Contains unpublished changes' across the top of the canvas"
    caption="State change iterations"
  />
</div>

<div class="grid gap-[var(--spacing-xl)]">
<h3 class="story-subhead">How to handle mandatory updates?</h3>
<p class={[storyProse, 'w-full max-w-[var(--measure-copy)] mx-auto'].join(' ')}>Mandatory updates are made by workspace admins, usually for security reasons. I decided to not emphasise updates as "mandatory" and bring them up only at the point of publish, incase the user had missed them, because builders have no choice but to accept them.</p>

  <Figure
    src={mandatoryUpdates}
    alt="Two versions of the publish-time dialog: the first lists each outdated dependency with its change description; the simplified one lists Connect Veeva and Slack with v3 → v4 and a single 'Update all and publish' action"
    caption="Mandatory update iterations"
  />

<div class="mx-auto w-full max-w-[var(--measure-copy)]">
<NoteBox title="Note on user testing" open>

Because conducting user tests with end users (e.g. CRAs) takes significantly longer to set up,
and we were on the clock with versioning, I validated these concepts with 5 internal users in
the client services team who use the product daily.

</NoteBox>
</div>

<Chapter id="constraints">
<StoryChapter heading="Constraints and bug fixes" narrow>

<div class="grid gap-[var(--spacing-xl)]">
<h3 class="story-subhead">Reduced scope to meet release dates</h3>
<p class={[storyProse, 'w-full max-w-[var(--measure-copy)] mx-auto'].join(' ')}>Engineering assessed that the complete design, including the settings side panel, would take longer than the release deadline allowed. Instead of pushing the date, I was asked for a middle ground. Everyone agreed the side panel was better UX, but it needed new components. So I cut it, because it fixed a consistency issue rather than anything crucial to versioning. As a result, I had to redesign the dependency card again to fit the existing, inconsistent modal.</p>

  <Figure
    src={scopeCut}
    alt="The dependency card in the consistent settings side panel, and the same card redesigned to fit the inconsistent Edit agent details modal"

<div class="grid gap-[var(--spacing-xl)]">

Because it was a purely front-end change, I didn't pull in a developer. I opened a branch in Cursor, tried a few iterations directly in code and raised a merge request in under an hour.</p>

<Chapter id="reflection">
<Reflection narrow>

Next time a deadline forces me to compromise on design, I'll get explicit agreement from the PM
to pick it up in the following release, with a ticket raised, so that the better UX stays
visible.

I also got to experiment with designing in code on this project. Based on that experience:

- Designing in code isn't suited to exploring diverse concepts; pen on paper is still the
  fastest.
- It shines on small problems with known solution patterns.
- It will empower design teams to own more of the front end.

At the end of the day, it's another tool in a designer's belt to reach for depending on the
situation. I also learned about code reviews and testing: I reviewed my own code and took
screenshots for testing, getting a small taste of developing and shipping something end to end.

</Reflection>
</Chapter>
