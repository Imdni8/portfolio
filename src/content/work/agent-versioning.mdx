<StorySection heading="Problem" divider>

> Without versioning, enterprise customers couldn't validate agents before releasing them.

<Term id="ai-builder">AI builder</Term> assembles an agentic workflow in Agent studio. For eg, a
<Term id="cra">Clinical Research Associate</Term> (CRA) responsible for maintaining compliance
can build an agent to monitor anomalies in the clinical trials they're responsible for.

Before versioning, editing an agent simply overwrote it and the changes went live immediately.
As a result, there was no way to implement any governance which allowed customers to validate
the changes before releasing it.

</StorySection>

<StoryChapter heading="Narrowing the problem">

<StoryBlock title="Studying existing platform patterns">

<Figure slot="visual" src={studyStatusChange} alt="Study Studio's change-status dialog, showing a current status of Draft moving to Publish" />

Before diving into ideation, I studied an existing pattern for status change in <Term id="study-studio">Study Studio</Term> (another product in the Medable platform) to see if I can use it in the context of agents. I found it inadequate for agents because…

1. **More UI manoeuvring:** A builder will receive updates on dependencies frequently. To
   change the status first, and then accept the new update would be intrusive UX.
2. **Misleading Mental modal:** Changing status from published to draft doesn't unpublish the
   agent (unlike the study, which becomes unavailable). For agents, changing state to draft is
   expected to create an identical version of the agent which user can modify, while the
   previous version stays published and available for use simultaneously.

</StoryBlock>

<StoryBlock title="Synthesising user requirements">

<Figure slot="visual" src={lifecycleMap} alt="A lifecycle map: draft to published v1 on first publish, then edit to draft and second publish to published v2" />

I began by mapping how versioning will change the existing workflow for AI builders based on
my product knowledge of agent studio.

After versioning, whenever a <Term id="dependency">dependency</Term> is modified, the agent
using it receives an update. I arrived at the following requirements for them.

1. They should be able to view it
2. They should be able to accept it only if they want to
3. In case the update is mandatory, they shouldn't be able to update the agent without
   accepting it
4. They should be able to rollback to a previous agent version

</StoryBlock>

</StoryChapter>

<StoryChapter heading="UX decisions">

<StoryBlock title="Designing new agent lifecycle patterns">

<Figure slot="visual" src={stateIterations} alt="Three iterations of the agent header comparing published and draft states, with the selected iteration at the bottom" />

> Version number is irrelevant. To help user track agent's lifecycle, anchor their attention to state

While ideating how to visualise agent's lifecycle, I realised the version number is not
important. The version can be v237. Therefore, user's mental model should be anchored in
canvas state so that it's clear which actions are allowed.

Therefore, the experience of versioning boils down to helping the user:

1. identify which state they are in currently, and as a result what they can do
2. clearly show when the state has changed
3. understand they have to republish for changes to take effect

</StoryBlock>

<StoryBlock title="Designing versioned dependency card">

<Figure slot="visual" src={dependencyCardIterations} alt="Three iterations of the dependency card, from a simple accept/dismiss affordance to the selected version-aware design" />

<NoteBox slot="visual" title="Note on user testing">

Because conducting user tests with end users (eg, CRAs) can take significantly longer to set
up, and we were on the clock with versioning, I validated these concepts with 5 internal
users in the client services team who use the product daily.

</NoteBox>

> Users want to know what changed in the update and both the previous and the latest version number

The dependency card was already crucial for editing the configuration of a dependency. Now
versioning was adding another layer of complexity.

To keep it simple, I began with a simple Y/N affordance to accept of dismiss updates
(iteration 1). But on viewing it with the user lens, it fell short because it didn't…

1. give any info to decide whether the new update was important
2. afford editing while it was also showing an update
3. accommodate multiple files under each dependency type

These points became the requirements for the 2nd iteration. But now the component felt too
busy. So for iteration 3, I took out the current version thinking it didn't add any value.

But on user testing iteration 3 with internal users, I learnt that they confused the version
number shown to be the existing version, not the new version. This was rectified in the final
iteration, which handled all requirements and scaled to all dependency types.

</StoryBlock>

<StoryBlock title="Enforcing mandatory updates">

<Figure slot="visual" src={mandatoryPublish} alt="A dialog listing dependencies with mandatory updates, blocking publish until all are accepted" />

<Term id="mandatory-update">Mandatory updates</Term> are crucial for security, and made by
workspace admins, hence builders have to accept it.

The key UX driver here was _when_ to bring the mandatory updates up and doing it without being
intrusive. If the user doesn't accept them on the canvas, instead of highlighting it, the more
thoughtful way to enforce it would be to bring them up at the point of publish so that the
user can accept them all in one shot.

I also debated whether mandatory updates should be highlighted on the canvas, exploring
various layouts like accordions and grids to list them. Finally, I decided the optimal UX was
to accept all mandatory updates in one go at the time of publish. A carousel works best
because it does not force the user to see all the updates, yet does not prevent them to go
through them if they want — <Term id="progressive-disclosure">progressive disclosure</Term>.

</StoryBlock>

<StoryBlock title="Showing versions and rollback">

<Figure slot="visual" src={versionsModal} alt="The versions modal: a dated list of versions on the left, the selected version's configuration in tabs on the right" />

> Modal can handle large number of versions. Arranging the version configuration in tabs keeps it easy to find for the user

Regarding versions, I knew the list could grow long, that's why I opted to navigate user to a
modal, where I can show large numbers of versions.

The meta data on version card was decided based on what users want to know—when was the
version created and by whom.

At first, I decided not to put the "published" tag assuming it would be obvious that the
version on top of the pile is the published, but during stakeholder discussion, I realised the
topmost version could be draft.

The content of each version was arranged in tabs for the following reasons:

1. make it easy for users (likely auditor or builder) to find what they are looking for
2. to avoid long scroll

</StoryBlock>

<StoryBlock title="Designing visual cues for state change and updates">

<Figure slot="visual" src={visualCues} alt="An accent-bordered node, a floating updates-available tab, and a banner reading 'This canvas contains unpublished changes'" />

I wanted to convey important information to the user about updates and state changes on the
canvas in a subtle way without demanding too much cognition from them. I achieved this using…

1. accent border to visually differentiate nodes with updates, making it easier to scan for
   updates.
2. a floating tab to convey total updates and accept all updates in one go.
3. a banner moving at the top when canvas changes to draft, clearly giving feedback of state
   change.

</StoryBlock>

</StoryChapter>
